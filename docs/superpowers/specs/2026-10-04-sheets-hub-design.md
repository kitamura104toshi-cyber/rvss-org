# スプシを中心にした新しい運用方式（新システム）設計

2026-10-04

## 目的

人が編集するデータの置き場所をGoogleスプレッドシートにまとめ、アプリは表示とアサイン編集だけを受け持つ形にする。
運営（core）がスプシで直接メンバー情報を直せるようにし、全データをスプシで見渡せるようにする。

## 前提：本番とは完全に別のシステム

- **dev を新システムとして育てる。** 最初に一度だけ本番のデータを dev に写し、その後は本番と同期しない
- **本番（今のアサイン管理表）には手を入れない。** 本番のアプリ（`index.html`／rvss-org-zeta）、
  本番Supabase（`dbrwsrrfmpnvpzxcdupp`）、その cron・Edge Function、バックアップブック（`1Avaf…`）は今のまま
- **新システムのアプリは別フォルダ。** 今の `index.html` は本番と共用なので書き換えない。
  `C:\Users\mr171\claude\RVSS\組織管理v2\` に複製し、独立した git リポジトリにする。当面はローカル（localhost）でだけ動かす。
  公開するときは新しいGitHubリポジトリと新しいVercelプロジェクトに出す（本番の Vercel には載せない）
- **新システムの Supabase は dev（`vsqrgcsobweaupiabagu`）。** 新アプリは接続先を dev に固定する（`IS_LOCAL_DEV` による切り替えは持たない）
- **本番と共有している取り込み元のシートは読むだけ。** 募集フォームの回答・契約（NDA）・採用管理（入会者）。
  新システムから書き込むのは、dev 用バックアップブック（`1j6rT…`）と、新しく作る2冊だけ

## タブの決まり

各タブは次のどちらかで、混ぜない。

- **編集タブ**：人が直す。スプシ → Supabase へ写す
- **写しタブ**：見るだけ。Supabase → スプシへ写す。名前に「（自動）」を付け、シート保護をかける。手で直しても次の同期で上書きされる

**新システムでは報酬の入力値をすべて月ごとに持つ。** 今は `compensation.members[氏名]` 直下に置いた値が全部の月に効く
（CLAUDE.md「報酬の月ごとの値」）。新システムでは直下の値を使わず、`byMonth["YYYY-MM"]` だけを見る。
移行時は、直下の値を、報酬の対象になっている各月（`compensation.exportSheets` のキーと、各人の `byMonth` にある月の和集合）の行に展開して書き出す。
その月の `byMonth` に同じ項目がすでにあれば、そちらを優先する。新アプリの報酬計算もこれに合わせて直す。

月ごとの報酬書き出しブック（`sheets-pay-export`）は今のまま、新しいブックを作って出す。

## データの流れ

```
人が直す  ：組織ブック「メンバー」・報酬ブック「月次入力」 ──5分ごと／ボタン──▶ Supabase ──▶ アプリ
アサイン  ：アプリ ──▶ Supabase ──5分ごと──▶ 組織ブック「…（自動）」
自動の取込：Notion・Canva・NDA・募集フォーム ──▶ Supabase ──▶ 組織ブック／報酬ブック「…（自動）」
入会者    ：採用管理シート ──毎日──▶ 組織ブック「メンバー」に行を追加 ──▶ Supabase
```

自動で入ってくるデータは、今ある取り込み（dev に入っている同じ関数）をそのまま使う。スプシを経由させない。
人が直さないデータなので経由させる利点がなく、月初の稼働時間の確定などを作り直す危険のほうが大きいため。

### 名簿の本体は「メンバー」タブ

- 行を足せば入会、状態を「退会」にすれば退会、「BS」にすればBS
- 入会者の自動取り込み（`sheets-intake-sync`）は、`org_state` に直接作るのをやめ、「メンバー」タブに行を足す。
  今の安全策（メアドで同一人物判定・カタカナ名は要確認・1回20名まで）はそのまま
- アプリからメンバーを足す・消す操作はなくす
- **行が丸ごと無くなった人は退会扱いにしない。** 警告を出すだけ（行の誤削除で名簿から人が消えるのを防ぐ）

## 同期の部品（dev の Edge Function）

### `org-sheets-pull`（新規）：編集タブ → Supabase

1. 「メンバー」「月次入力」を読む。列は見出し名で引く（`findCol`／`normalizeHeader`）
2. 必須の列（氏名・状態／月・氏名）が無ければ、**何も書かずにエラー**
3. 担当する項目だけのパッチを作る：
   `members`／`deletedMembers` の在籍・退会、`memberOverrides[氏名]` の上の表の項目、`compensation.members[氏名].byMonth[月]` の上の表の項目
4. SQL関数 `apply_sheet_patch(patch jsonb)` で、**1回のUPDATEの中で既存の値にマージ**する。
   「全体を読む → 直す → 全体を書く」をしない（その間にアプリで保存されたアサインを消さないため）
5. 空欄は空として書く（スプシが本体なので、消した値はアプリでも消える）
6. 結果を `state.sheetSync`（`pulledAt`・`error`・`warnings`）に残す

`dryRun: true` なら書かずに、変わる予定の項目の一覧を返す。

起動：cron 5分ごと、アプリの「今すぐ反映」ボタン。

### `org-sheets-push`（新規）：Supabase → 写しタブ

- 写しタブを毎回消して書き直す。今の `sheets-backup`／`sheets-area-list` の作り方を使う
- 前回の書き出し以降に `org_state.updated_at` が変わっていなければ何もしない
- 結果を `state.sheetSync.pushedAt` に残す

起動：cron 5分ごと。

## アプリ（新アプリ）の変更

- 接続先を dev Supabase に固定する
- メンバー情報・報酬入力・募集の進捗は**表示だけ**。編集フォームの代わりに「スプシで編集」リンク（該当タブを開く）
- アサインの編集は今のまま
- core 以上に「今すぐ反映」ボタン。`org-sheets-pull` を呼び、`sheetSync` の時刻・エラー・警告を出す
- 報酬計算は `byMonth` の値だけを見る（上の「月次入力」の節）
- `transition`（新体制への移行）タブを外す

## 同時に書いたときのこと

アプリは保存のとき state 全体を書く。アプリが古い state を持ったまま保存すると、直前の pull の結果を巻き戻すことがある。
- アプリはリアルタイム購読で他の更新を受け取るので、この窓は短い
- pull は同じ内容を何度書いても結果が変わらないので、巻き戻っても5分以内に戻る

逆に pull がアサインを消すことはない（担当項目だけを1回のUPDATEでマージするため）。

## 移行の手順（すべて dev）

1. 今の dev の `org_state`（id='main'）を `backup-20261004-pre-v2` に退避する
2. 本番の `org_state` を dev へ写す（最後の同期。以後は写さない）
3. 北村さんが組織ブック・報酬ブックを作り、bot に編集権限を共有する
4. 新アプリのフォルダを作る（`index.html` を複製し、接続先を dev に固定）
5. 今の Supabase の内容を、編集タブへ一度だけ書き出す（直下の報酬値は月ごとの行へ展開）
6. `org-sheets-pull` を `dryRun` で走らせ、**差分がゼロ**であることを確かめる。ゼロでなければ先へ進まない
7. 新アプリの編集を切り替える
8. dev の cron を再開し、pull・push を加える。`sheets-intake-sync` は書き込み先を変えてから再開する

本番はこの手順のどこでも触らない。

## 確かめること

- 書き出し → 読み戻しで差分がゼロ
- スプシで直した値が5分以内（ボタンなら即時）にアプリへ出る
- pull とアプリでのアサイン保存が重なっても、アサインが消えない
- 必須の見出しを消すと、何も書かずにエラーで止まる
- メンバーの行を消しても退会扱いにならず、警告が出る
- 共有している取り込み元のシート（募集・契約・入会者）に、新システムから書き込みが起きていない
- 本番の `org_state.updated_at`・本番バックアップブックが、作業の前後で新システム由来の変化をしていない

- 新システム用のCanva週1取り込み
